# Test Coverage Matrix

> **Snapshot: 2026-10-12, work package QA-1.** This records what the automated suite in
> `apps/api/test/` actually proves, row by row. Evidence was taken by reading what each
> `it()`/`test()` asserts — never inferred from a file name. Re-verify before relying on a
> row: code and tests move. To run the suite and read its report, see
> [`apps/api/test/README.md`](../../apps/api/test/README.md).

**How to read a row.** "Coverage evidence" names the test file and the `it()` name whose
assertions prove the row. **MISSING** means no test exercises it. **UNKNOWN** means this
inventory could not settle it. Priorities: **P1** = a regression here could silently break
a core workflow or a security boundary; **P2** = important but contained; **P3** = nice to
have.

Common to every DB-backed row: the test type is an integration test using `node:test` plus
`fastify.inject()` against the real app (`test/helpers/build-app.js`) and a real Postgres.
Data comes from the shared factories (`scenarios/factories.js`), tagged `__wp1_test__` and
deleted after each file. It runs on every `npm test` / `npm run ci`, locally and in the CI
**Lint & Test** job (`.github/workflows/deploy.yml`) against a disposable Postgres service
container. There is **no staging run**: the staging workflow is inert, because there is no
staging host (`docs/DEPLOYMENT.md`).

## Characterisation findings (do not change code)

Open questions for the owner, not fixes. Each was checked against the code on 2026-10-12.

- **F1 — CONFIRMED.** No single electrician is ever selected. On a public complaint, `public.js:409-418` notifies **every** worker that `getAssignedWorkerIds` (`assignment-resolver.js:79-108`) returns, collectively, via `notifyWorkers`. `ticket.assignedToId` is a **User** (supervisor) relation (`schema.prisma:255-256`), set from `supervisorIds[0]` (`public.js:360`). A worker's pickup (`worker-auth.js:655+`) moves the ticket to IN_PROGRESS and connects the worker to `resolvedWorkers`; it does not set an assignee.
- **F2 — RESOLVED 2026-10-13 (WP-H).** `assignment-resolver.js` `rankAssignees()` now orders: direct assignment, then nearest ancestor, then `isPrimary` (workers only), then `createdAt`, then `id`. Tests: `approved-fixes.test.js` › "the nearer covering supervisor comes first, identically over 5 calls", "a direct assignment at the location beats any ancestor", "a public complaint and an internal ticket are both assigned to the nearer supervisor", "workers: nearest first, then isPrimary, then createdAt". *Original finding:* `public.js:360` sets `assignedToId: supervisorIds[0] || null`. `supervisorIds` comes from `prisma.supervisorAssignment.findMany` with **no `orderBy`** (`assignment-resolver.js:122-133`), passed through a `Set`. Which supervisor is "first" is therefore whatever order Postgres returns. The same pattern applies to internal tickets (`tickets.js:156-157`).
